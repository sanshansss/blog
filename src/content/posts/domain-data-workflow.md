给领域智能体准备数据，难点往往不在“让模型读懂一段话”，而在**一条端到端链路的断层**：源头 URL 散落难找、页面形态与单位五花八门；好不容易洗干净存下来，如果存储形态和智能体调用方式不匹配，模型在推理时依然会“瞎猜”或“算错”。

结合此前做卫星规格库与 GNC 单机器件库的实践，前面几个环节其实可以收拢成一条紧凑的工程链路，而真正拉开差距的，往往在“拿到数据”之后。

## 一、数据从来源到可用的几个关键卡点

把领域数据真正喂给智能体，通常会连续卡在四个衔接处：

- **找源与对齐基数**：很多采集方案默认“URL 列表已经摆在桌上”，但垂类数据源往往散落在分页检索接口、新闻通告和 PDF 附件里。拿到链接后，还要先算清“来源基数”与“实体基数”的映射——比如卫星数据采集中，3,271 条记录去重后只有 1,494 个 URL，66% 的卫星共用来源，单个 URL 最多被 74 颗星共用（多半是同一篇发射报道）。不算清这层关系，直接按页面切块入库，就会把同一篇文章拆成几十个重复或串台的样本。
- **按形态抽取与量纲归一化**：静态/服务端渲染页适合 `requests` 去噪后用强约束 Schema 做槽位填充；前端动态渲染的表格页，直接在浏览器控制台跑 DOM 脚本导出 JSONL 往往更省事。抽取之后真正的重活在**归一化**——质量（`kg` / `g`）、力矩（`N·m` / `mN·m`）、指向精度等物理量必须统一量纲并保留原始值溯源，同时把测试工况和“未披露/不适用”这类空值语义拆出来。
- **分形态存储**：别把所有东西塞进同一个桶。**结构化参数库**（SQL / JSONL）存精确指标、标准量纲与型号清单，负责“算得准、筛得准”；**非结构化/半结构化证据库**存背景说明与设计约束，强制绑定 `source_url`、抓取时间与原文片段，负责“说得清、有依据”。
- **按问题类型接入推理**：原理、方案对比与规范依据走 RAG / 图谱检索，靠证据链组织回答；型号筛选、指标比对和物理量核算则强制走 SQL 查询与计算工具，不让模型心算或凭印象报数。

## 二、数据只是第一步：终点是 Environment 与 Tools

把上面这套链路跑通，其实只完成了“拿到可用数据”的第一步；而在很多垂直领域，连这一步都远未做好。再往深处看，还会遇到一个更根本的问题：**为什么领域 AI 的落地，还是远不如写代码和做数学那样顺畅？**

最近看到 [noahatwhere 关于“RL 环境公司”的讨论](https://x.com/noahatwhere/status/2125552449054491011)，把这件事点得很透：

> 代码和数学之所以先爆发，本质上是因为编译器和证明器天然就是完美的 RL environment，有极其清晰的 verifiable rewards。但现实世界的绝大多数商业场景——供应链调度、客服售后、金融风控、法律合规、医疗诊断——全都没有现成的 gym。

顺着这个逻辑看，未来垂直领域要真正用好 AI，重点会从“静态语料”转向**可验证的交互环境**：

- **对内是基础设施重构**：想让 Agent 真正接管复杂流程，光靠几页 SOP 文档和静态知识库是不够的，必须把内部的 API、数据库、审批流和历史边界案例，打包成一个可重置、可沙盒模拟、有明确奖惩机制的仿真环境，让 Agent 在里面跑通足够多的试错与评测，再放到线上干活。
- **对外是护城河的重定义**：静态数据库与零散经验如果不结构化、不闭环，很快会被贬值；真正稀缺的，是行业独有的**状态转移逻辑和反馈闭环**——即“在这个领域里，到底什么才算干得漂亮”。

把这个视角拉回航天领域，感受会尤其强烈：

1. **数字化前置缺失**：由于航天行业的保密属性，大量工程数据、设计经验与型号细节本身的数字化、结构化就远未完成，更谈不上直接做数智化与 Agent 化。从当前通用大模型（如 GPT、Gemini、Claude 等）在航天专业问题上的回复也能明显感受到，它们的领域世界知识依然不够扎实。
2. **缺少“Blender 级”交互软件与可验证器**：今天的大模型配合 Blender 可以做出非常惊艳的 3D 建模，前提是存在标准化的交互软件、丰富的操作数据以及所见即所得的渲染反馈；但航天领域既缺乏类似 Blender 这样开放、易接入、能让模型学习“如何操作工具完成设计”的标准化软件与数据，也不像数学问题那样有 Lean 解析器、像代码那样有编译器可以提供低成本的确定性验证。

因此，当数据链路打通之后，后续的演进实际上会分化为两条清晰但互补的工程路径：

- **做垂类模型 $\rightarrow$ 核心是构造 Environment**：把领域内的物理方程、仿真器、工具接口与约束校验器封装成可交互、可重置、带明确反馈信号（verifiable rewards）的环境，让模型在与环境的闭环交互中习得领域策略，而不仅仅是背诵静态文本。
- **做垂类智能体 $\rightarrow$ 核心是建设 Skills / MCP / Tools**：在当前基座模型的能力边界内，把前序沉淀下来的结构化数据库、证据库、行业计算程序与工程工作流，封装成语义清晰、边界明确的 Skills、MCP 服务与确定性 Tools，让模型专注做意图理解与任务编排，把精准检索、数值计算与合规校验交给工具层。

## 三、小结

领域智能体的数据工作流，表面上看是一条“找得到源 $\rightarrow$ 抽得稳字段 $\rightarrow$ 齐得了量纲 $\rightarrow$ 接得上推理的工程链路；再往深处看，它实际上是在为上层的 **Skills / MCP / Tools** 准备确定性底座，也在为更长期的 **Environment** 建设积累状态定义与约束边界。

工程骨架可以复用，但每个领域的源头分布、单位方言、隐性规则和验证方式都得自己趟一遍——把数据底座打实，再去补齐工具与环境，垂类智能体才能从“能聊几句专业术语”，真正走向“能进工程闭环干活”。
